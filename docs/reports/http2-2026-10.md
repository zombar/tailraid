# HTTP/1.1 and cleartext HTTP/2 for the node RPC

Measured 2026-10-13 to decide whether the node RPC (`internal/rpc`) should move from
HTTP/1.1 to cleartext HTTP/2 (h2c with prior knowledge). The benchmarks are
`internal/rpc/http2_bench_test.go`; the raw output, three runs of each, is
`bench-2026-10-http2.txt` beside this file. Nothing in the node changed.

## Method

Each "host" is a real HTTP server on a loopback TCP listener. Every connection to a host
goes through a link that delays each write by a one-way latency and paces it through a
bandwidth that every connection to that host shares, per direction. One TCP connection and
many therefore compete for the same pipe, as they do on a tailnet path between two
devices. Two paths:

| Profile | One-way delay | RTT | Bandwidth per host and direction | Stands for |
|---|---|---|---|---|
| `lan` | 0.25 ms | 0.5 ms | 100 MiB/s | wired LAN, direct Tailscale path |
| `tailnet` | 7.5 ms | 15 ms | 25 MiB/s | Wi-Fi, a DERP-relayed or longer path |

Three client and server settings:

| Setting | Transport |
|---|---|
| `h1` | today's: HTTP/1.1, `MaxIdleConnsPerHost` 32 (I-255), `ResponseHeaderTimeout` 10 s, 3 s dial |
| `h2` | the same `http.Transport` with `Protocols` set to unencrypted HTTP/2 only (prior knowledge), the server accepting HTTP/1.1 and h2c; Go's default windows (server receive 1 MiB per stream and per connection, client receive 4 MiB per stream) |
| `h2-4MiB` | `h2` with `HTTP2Config` receive windows of 4 MiB per stream and 32 MiB per connection on both ends |

A shard is 1,468,006 bytes, a 4 MiB chunk at 3+2. The workloads:

| Workload | What it does | Stands for |
|---|---|---|
| PutFanout five-hosts | 8 workers, each PUTting one chunk's 5 shards to 5 hosts at once | the flusher, `ChunkWorkers` 8 (docs/04 §9) |
| PutFanout one-host | the same, all 5 shards to one host | the most one connection carries |
| HedgedGet | 8 workers, each GETting 4 shards and cancelling the last once 3 arrived; host 3 has a quarter of the bandwidth, so its GET is cut mid-body | the hedged read |
| ReadaheadSeek | 2 workers, each reading 1 shard and cutting 3 prefetches after 64 KiB | readahead cancelled by a seek (I-203) |
| ControlBurst | 32 apply calls at once (200 B in, 100 B out) to one host | proposals forwarded to the leader (I-255) |
| MixedRepairAndControl | 4 background shard GETs streaming from a host while single apply calls run against it | a repair pass beside a gateway's control traffic |

Each workload runs once untimed to open the connections a steady state keeps; `conns/op`
counts the TCP connections opened after that, per operation. Environment: Apple M2 Max,
macOS, Go 1.27.2, `-benchtime 40x`, `-count 3`; the tables give the median of the three.

## Reading

Throughput is the same within a percent everywhere. The shared link is the limit, as it is
between two real devices, and neither protocol moves bytes through it faster. HTTP/2's
default windows did not throttle a 1.4 MiB shard on either path: Go's server window of
1 MiB is refilled as the handler reads, and at 15 ms RTT that keeps up with 25 MiB/s.
Raising the windows to 4 MiB bought nothing in throughput and made the one-host p99 worse
(3.34 s against 2.26 s on the tailnet path): with bigger windows more streams of one
connection run at once, and the last of them finishes later.

What HTTP/2 changes is connections. On HTTP/1.1 a cancelled request closes its TCP
connection: a hedged read's loser costs 1.5 new connections per read, a seek that cuts
three prefetches costs 3, and even the steady PUT fan-out opens 0.9 a chunk (Go retires a
connection whose request it gave up on). Each new connection is a TCP handshake, one RTT,
plus slow start from a small window. On the tailnet path that shows as ReadaheadSeek's p99
of 533 ms against 464 ms on HTTP/2, which cancels a stream with RST_STREAM and keeps the
connection. Every other p99 moved by less than the noise of a run.

Small calls got slightly slower on HTTP/2: a burst of 32 apply calls has a p99 of 1.76 ms
against 1.06 ms on the LAN path, and 24.6 ms against 18.6 ms on the tailnet path. 32
streams share one connection's frame writer and one TCP send window, where HTTP/1.1 had 32
connections each sending its own small request. It is a few milliseconds on a path the
leader's Raft round trip already dominates.

The mixed workload shows no head-of-line difference: a control call waits behind the
background GETs' bytes either way, because both share one link. The benchmark has no
packet loss; with loss, HTTP/2 puts every stream of a host behind one TCP connection's
retransmission, where HTTP/1.1 stalls only the connection that lost the packet. On Wi-Fi
and relayed paths that is the case that matters, and this rig does not measure it.

## Trade-offs for tailraid

- **Rolling upgrades.** An h2c client with prior knowledge sends the HTTP/2 preface and
  nothing else, and an old node serving HTTP/1.1 answers it with a 400 or a reset. A move
  needs a gate: speak h2c only to a node whose row reports a version that serves it (the
  member table carries `Version`), or keep HTTP/1.1 and enable h2c on the server first, a
  release before any client uses it. The HTTP/1.1 `Upgrade: h2c` path avoids the gate but
  costs a round trip per connection and Go's client does not offer it.
- **Loss on one connection.** All of a host's traffic, shard bodies, control calls and
  `/health` probes, rides one TCP connection. A lost packet on a Wi-Fi link stalls all of
  it for a retransmission timeout, and a probe that misses its deadline marks the host
  suspect (I-170). HTTP/1.1 spreads the same traffic over many connections, which also
  share congestion control less fairly with other users of the link.
- **Flow-control windows.** Go's defaults suit 1–4 MiB shards. A larger window only lets
  more of one connection's streams run at once and stretches the tail.
- **Cancellation.** HTTP/2's main gain: cancelling a losing hedge or a readahead stops one
  stream and keeps the connection warm. On HTTP/1.1 every cancellation is a new handshake
  and a cold TCP window.
- **Timeouts and the busy reply.** `ResponseHeaderTimeout` (I-83) works per request on
  both. The busy reply of I-246 is an ordinary 503 on both. HTTP/2 adds a connection-level
  failure mode HTTP/1.1 does not have: a stalled connection fails every stream on it at
  once, so one slow transfer can take a host's probe with it unless `ReadIdleTimeout` and
  `PingTimeout` are set.
- **Memory.** HTTP/2 holds a receive window per stream; at Go's defaults that is at most
  1 MiB per incoming stream on the server, within the slot budget of I-83. It saves the
  per-connection buffers and goroutines of 32 idle HTTP/1.1 connections per peer.

## Recommendation

Do not switch now. Throughput and latency are the same within noise on every bulk
workload, small control bursts got a few milliseconds slower, and the one clear gain, 0.9
to 3 fewer TCP handshakes per cancelled or retired request, is worth about 70 ms of p99 on
a cancelled readahead over a 15 ms path. Against that stand a rolling-upgrade gate and a
new single-connection failure mode on lossy links that this rig cannot measure. If the
connection churn becomes visible on the real cluster (handshakes per second in
`status`, or readahead tails after seeks), the cheaper step is to stop cancelling
mid-body on HTTP/1.1 where the remaining bytes are few, and to revisit HTTP/2 behind a
version gate with a loss test first.
