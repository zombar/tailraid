# 10 — S3: API gateway and remote S3 storage nodes

> **Status.** The storage nodes of §4 are built (2026-10-10): `internal/s3` signs and
> sends the requests, `node add-s3` registers a bucket and `node keys` gives a device its
> credentials. The API gateway of §3 is deferred (2026-10-08): its invariants (I-19, I-20,
> I-21, I-51, I-54, I-55) and the gateway cells (L-24, L-25) remain skipped stubs in
> `test/invariants`.

Two uses of the S3 protocol, one lightweight implementation of our own (no AWS SDK, no
minio-go):

1. **API gateway** (`internal/s3srv`): every device serves an S3-compatible API over the same
   `vfs` as NFS, so tools and devices without an NFS client read and write the volume.
2. **Storage nodes** (`internal/s3` client): an S3 bucket at any provider acts as a
   storage-only node holding shards, placed and repaired like a device.

Shared package `internal/s3`: SigV4 sign + verify, XML types, error codes, client.

## 1. Why our own

`aws-sdk-go-v2`, `minio-go` (225 require lines) and `gofakes3` (depends on the AWS SDK) each
drag hundreds of modules into `go.sum`. Our subset is small, stable and fully exercised by
our own tests, and the server over an in-memory billy fs is also the test fake for the
client. Both sides are therefore tested against each other and, gated on credentials,
against real providers.

## 2. SigV4

Supported: `Authorization: AWS4-HMAC-SHA256 Credential=<key>/<date>/<region>/s3/aws4_request,
SignedHeaders=..., Signature=...` with `x-amz-date` (or `Date`), `x-amz-content-sha256` ∈
{hex sha256 of body, `UNSIGNED-PAYLOAD`, `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` (aws-chunked,
needed by the AWS CLI; decoded, chunk signatures verified)}. Presigned query-string auth
(`X-Amz-Algorithm=...`) is accepted for GET only. Clock skew window ±15 min. Region is
accepted as any string and echoed; our region name is `tailraid`.

```go
// internal/s3
type Credentials struct { AccessKey, SecretKey string }
func Sign(req *http.Request, c Credentials, region string, payloadHash string, now time.Time) error
func Verify(req *http.Request, lookup func(accessKey string) (secret string, ok bool), now time.Time) (accessKey string, err error)
// Verify recomputes the canonical request from SignedHeaders only, compares with constant time.
```

Canonicalization follows the AWS spec: URI-encode each path segment (encode `/`? no),
sort query params, lower-case header names, trim values, `host` always signed.

## 3. API gateway (`internal/s3srv`)

Listener `<tsIP>:20443` and `127.0.0.1:20443`, plain HTTP (WireGuard encrypts the tailnet;
loopback is local). Every request must pass **both** a WhoIs check that the source is a
tailnet identity (any tailnet node by default, so phones and Windows Home machines can use
rclone; `s3.members_only: true` in the config tightens this to cluster members through the
same `rpc.Authorizer`; loopback is trusted) and SigV4 with an access key from
`<config>/s3keys.yaml` (0600, managed by `tailraid s3 keys`). Path-style addressing only
(`/bucket/key`); virtual-host style is not supported (no DNS control on a tailnet).

### 3.1 Bucket and key mapping

- Bucket = top-level directory of the volume. `ListBuckets` = `ReadDir(root)` filtered to
  directories, excluding names starting with `.`.
- Key `a/b/c.txt` in bucket `B` = path `/B/a/b/c.txt`. Intermediate directories are created
  on PUT (`MkdirAll`) and never auto-deleted.
- A key ending in `/` denotes a directory: `PUT` with empty body → `Mkdir`; `DELETE` →
  `Rmdir` (fails `BucketNotEmpty`-style with `409` if non-empty).
- Rejected with `400 InvalidArgument`: empty segments (`a//b`), `.` or `..` segments, keys
  > 1024 bytes, bucket names not matching `[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]`, and any name
  starting with `.` (reserved for `/.tailraid/`).
- Directories appear in listings only as `CommonPrefixes` when a delimiter is given, or as
  zero-byte keys ending in `/` otherwise (matches how rclone/s3fs create "folders").

### 3.2 Operations

| Operation | Method / path | Behaviour | Status |
|---|---|---|---|
| ListBuckets | `GET /` | dirs of root | 200 |
| HeadBucket / CreateBucket / DeleteBucket | `HEAD/PUT/DELETE /b` | Stat / Mkdir / Rmdir(empty) | 200, 404 NoSuchBucket, 409 BucketNotEmpty |
| ListObjectsV2 | `GET /b?list-type=2&prefix&delimiter&start-after&continuation-token&max-keys` | §3.3 | 200 |
| ListObjects (v1) | `GET /b?prefix&marker` | thin wrapper over v2 | 200 |
| PutObject | `PUT /b/k` | stream → `OpenFile(O_CREATE\|O_TRUNC)`, `Write`, `Close`; verify `Content-MD5` / payload sha256 if given; set ETag | 200, 400 BadDigest / InvalidDigest |
| GetObject | `GET /b/k` | `ReadAt` with `Range` (single range, `bytes=a-b`, suffix form) | 200, 206, 404 NoSuchKey, 416 |
| HeadObject | `HEAD /b/k` | attrs only | 200, 404 |
| DeleteObject | `DELETE /b/k` | `Remove`; missing key is still 204 | 204 |
| DeleteObjects | `POST /b?delete` | up to 1000 keys, per-key result XML | 200 |
| CopyObject | `PUT /b/k` + `x-amz-copy-source` | source is flushed on this gateway (`FlushInode` + `WaitApplied`) then its chunk list is copied via `Commit` (no data movement; dedup) | 200 |
| CreateMultipartUpload | `POST /b/k?uploads` | mkdir `/.tailraid/uploads/<id>/`; `id` encodes this node's ID, and every later call for `id` must arrive at the same gateway (others answer `404 NoSuchUpload`) | 200 |
| UploadPart | `PUT /b/k?partNumber=n&uploadId=id` | PUT to `/.tailraid/uploads/<id>/<n>`; part ETag = MD5 | 200, 404 NoSuchUpload on another gateway |
| CompleteMultipartUpload | `POST /b/k?uploadId=id` | §3.4 | 200, 400 InvalidPart / InvalidPartOrder, 400 EntityTooSmall |
| AbortMultipartUpload | `DELETE /b/k?uploadId=id` | remove staging dir | 204 |
| ListParts / ListMultipartUploads | `GET ...?uploadId` / `GET /b?uploads` | from staging dirs | 200 |
| Everything else (versioning, acl, policy, lifecycle, tagging, cors, website, object-lock, sse, select, presigned POST) | — | `501 NotImplemented` XML error | 501 |

GET/HEAD support `If-Match`, `If-None-Match` (→ 304 / 412), `If-Modified-Since`,
`If-Unmodified-Since`. PUT supports `If-None-Match: *` (create only → 412 if exists).

### 3.3 ListObjectsV2 over the FSM

Keys under a bucket are enumerated in UTF-8 byte order by a depth-first walk of the FSM
(`ReadDir` returns names sorted). With `delimiter="/"` the walk does not descend below the
first delimiter after `prefix` and emits `CommonPrefixes`. `continuation-token` is the last
key returned (opaque to clients: base64 of it); `start-after` is the same mechanism. The
walk is resumed by descending along the token's path, so each page costs O(depth + page).
Because every page is computed against the then-current FSM, concurrent writes may add or
remove keys *between* pages; I-21 guarantees that keys existing for the whole listing are
returned exactly once and in order. `max-keys` default 1000, cap 1000.

### 3.4 Multipart completion

Parts are ordinary files under `/.tailraid/uploads/<id>/<partNumber>` (hidden from listings,
excluded from `bucket ls` sizes). A multipart upload is **bound to the gateway that created
it**: `uploadId = <nodeID>-<random>`, and `UploadPart`, `Complete`, `Abort` and `ListParts`
on any other gateway answer `404 NoSuchUpload`. This is what lets Complete rely on the parts'
chunk lists being final. Stale uploads (no part activity for 7 days) are removed by the
gateway that owns them, on a daily timer, and a gateway that restarts adopts its own stale
uploads from the directory names. On Complete:

1. Validate order and ETags; all parts except the last must be ≥ 5 MiB.
2. `FlushInode` + `WaitApplied` for **every** part (they are this gateway's own dirty
   files, so this is local), so each part's committed chunk list is complete.
3. If every non-final part's size is a multiple of `ChunkSize` (true for the common 5/8/16/
   64 MiB part sizes with a 1 MiB chunk), the object's chunk list is the concatenation of the
   parts' chunk lists: one `Commit` on the target inode with `Writes` built from the parts'
   hashes and `NewSize = Σ sizes`; refcounts move, no bytes move.
4. Otherwise fall back to streaming the parts through `File.Write` (correct, just slower).
5. ETag `"<md5(concat of part MD5 digests)>-<N>"`, stored as an inode attribute? No: ETags
   are **derived**, not stored. Single-part ETag = MD5 of content; `s3srv` keeps a small
   on-disk LRU `etag/<ino>.<version>` so HEAD after PUT does not re-read the object, and
   recomputes on miss. Multipart ETags are stored in the same cache at Complete time.
6. Remove the staging directory after the Commit is applied.

### 3.5 Access keys

`tailraid s3 keys create [--name]` prints an access key (20 chars) and secret (40 chars)
once; stores `sha256(secret)`? No: SigV4 needs the secret, so the file stores it in
plaintext with mode 0600 (OS keyring when available, as errol does). `revoke`, `ls`. Keys
are per device (not replicated); a key works on every gateway only if created on each, or
copied. This is deliberate: secrets stay out of Raft.

## 4. S3 storage nodes

A bucket is a placement target with no process of its own: every device that holds its
credentials reads and writes it directly, the leader places shards on it as on a disk, and
nothing in the bucket is ever coordinated, because an object key names its content.

### 4.1 Node record and credentials

The node record is the single `meta.Node` struct of `docs/01` (`Kind == KindS3`); the S3
fields are `S3Endpoint` (a URL: `https://s3.eu-central-003.backblazeb2.com`, or `http://`
for a MinIO on the tailnet), `S3Bucket`, `S3Prefix`, `S3Region` (`us-east-1` when empty)
and `S3PathStyle`, and `Capacity` is the placement weight and the budget `status` counts in the volume's
capacity; tailraid never enforces it (the provider decides when a bucket is full, and a
refused PUT is a failed slot like any other). The row's domain is itself (14 §5), so it is one host to the host cap and to
`AutoPolicy` (03, 14 §6). Device-only fields are left empty.

Credentials are **never** in the FSM, a report or a request to another node (I-139). Each
device keeps them in `<data_dir>/s3nodes.yaml` (mode 0600), keyed by the S3 node's name:

```yaml
offsite:
  access_key: 0035a…
  secret_key: K003…
```

`serve` rereads the file when it changes, so a key added on a running device is used within
one probe interval. A device without credentials for an S3 node treats it as unreachable
for its own reads and writes and its probe reports it dead, so `status` on that device
shows the row not live.

**Registering.** `tailraid node add-s3 <name> --endpoint URL --bucket B [--prefix P]
[--region R] [--path-style] --capacity SIZE --access-key KEY` reads the secret key from
`TAILRAID_S3_SECRET_KEY` or, failing that, one line of stdin (never a flag: it would sit in
the shell history), checks the bucket with a round trip (PUT, GET and DELETE of
`<prefix>/tailraid-check`, so a key without write or delete rights is refused before
anything is registered), asks the leader for `add_s3`, and only then writes the
credentials to this device's file, so a refused add leaves no key behind. The row's ID is
drawn by the CLI, so a retry after a timeout updates the row it created (I-62). The
leader refuses (I-137):

- a name that a row which is not removed already has (credentials are keyed by name);
- an endpoint and bucket that an S3 row which is not removed already has, under any prefix:
  two rows over one bucket are one failure domain that placement would count as two, and
  two prefixes of one cluster gain nothing. Two **clusters** may share a bucket under
  different prefixes; each one's sweep sees only its own prefix;
- an endpoint that is not an `http` or `https` URL, an empty bucket, or a zero capacity.

`tailraid node keys <name> --access-key KEY` (secret as above) writes the credentials on
another device and checks them with a HEAD of the bucket. A device that flushes needs the
key: without it every slot it would place on the bucket stays 0 until the leader's repair
fills it. Removing an S3 node is `node drain`, then `node remove` once its slots are gone
(02 §Lifecycle commands); the objects are left in the bucket for the operator to delete.

S3 nodes are storage-only: never Raft members, never gateways, no `/health`, no WhoIs.

### 4.2 Shard routing

`rpc.Client` is the shard client of every node (`chunk.ShardClient`); a target that is an
S3 row goes to its bucket instead of a host:

```go
// rpc
func (c *Client) SetS3(b func(meta.NodeIdx) (bucket *s3.Bucket, isS3 bool))
// node: the buckets of the member table, rebuilt when a row or the credentials change
```

Object key for shard `<hex>.<k>-<m>.<idx>`: `<Prefix>/shards/<hh>/<hex>.<k>-<m>.<idx>`
(`shards/…` with no prefix) — the same layout as a disk's `shards/` directory, so a bucket
can be inspected or mirrored with any S3 tool and the two "volume formats" are identical.
The object body is the same `TRS1`-headed file as on a disk (I-52). `PUT` sets
`x-amz-content-sha256` to the body hash so the provider verifies integrity on upload, and a
dup PUT to S3 **always overwrites** (there is no cheap header compare; the fresh
`LastModified` is the S3 equivalent of the mtime refresh). `GET` verifies the header hash on
receipt exactly as for disk shards (I-11 applies to the bytes we store, regardless of
where) and reports `ErrCorrupt` for an object that fails it; `HEAD` answers `Has`.

**Deletes.** `Delete` and `DeleteFenced` on an S3 target are refused without a request
(`ErrFenced`, which the GC worker and the repairer count as refused): the fence that
protects a disk shard (the target's host has applied the index, the shard is older than
grace, 06 §2) has no counterpart on a bucket. Objects leave a bucket only through the
leader's S3 sweep (06 §3, I-138), which lists the prefix and deletes what the chunk table
does not place there and is older than grace.

### 4.3 Liveness and ranking

Every node probes each S3 node itself with `HEAD /<bucket>` every 30 s (S3 liveness is
not in Raft and the leader's view would not be available on followers); a bucket is live
within 90 s of its last good probe. A probe needs the credentials: without them the row is
dead on that node. `Peers.Rank` orders S3 nodes **last**, so reads touch the bucket only
when a device holding a needed shard is down (L-104). `fill_after` and `evict_after` apply,
judged by the leader's own probe.

### 4.4 Flush behaviour

PUTs to S3 run in the same parallel fan-out; the flush proceeds once ≥ k acks (from any
nodes, device or S3) arrive and either all PUTs finished or the 10 s deadline passed (04 §4
step 9). A slow bucket therefore never stalls the WAL drain; its slot is recorded as 0 and
the repairer fills it with no deadline (I-53, L-48).

### 4.5 Client policy

`s3.Bucket`: HTTP/1.1 keep-alive, 8 connections per host, a request deadline of 30 s plus
the body at 256 KiB/s (a DERP-relayed tailnet path or a slow uplink), up to four attempts
with exponential backoff and jitter on 5xx, 429 (`SlowDown`) and connection errors;
**never** on another 4xx; `ListObjectsV2` pages of 1000 for the leader's S3 sweep. Costs:
a 1 MiB chunk at 2+1 is three 512 KiB objects; `init --chunk 4MiB` is recommended for
S3-heavy volumes.

### 4.6 Future (documented hooks, not barebones)

- `role: parity-preferred` on a node: `Place` fills parity slots from such nodes first so a
  bucket holds parity only and bulk reads never touch it — off-site redundancy of a RAID
  volume.
- Snapshot backup: the leader uploads each Raft snapshot (and a log tail) to
  `<Prefix>/meta/`, closing the "lost Raft majority" hole for metadata.

## Invariants

- **I-19** — An object written through the S3 gateway is byte-identical when read through NFS (and vice versa) on any gateway, after the write is acknowledged.
- **I-20** — The S3 gateway returns 200 for PutObject and UploadPart only after the corresponding vfs `Close()` has succeeded (WAL fsynced, same contract as an NFS WRITE), and for CompleteMultipartUpload only after every part has been flushed and the splice Commit applied; a failure yields a 5xx and the object is unchanged.
- **I-21** — ListObjectsV2 returns every key that existed for the whole duration of a paged listing exactly once, in UTF-8 byte order, across all continuation tokens; no key is duplicated or skipped.
- **I-51** — SigV4 verification accepts a request iff its signature was produced with the secret of a currently valid access key over the signed headers and payload hash, within the skew window; verification does not depend on unsigned headers.
- **I-52** — A shard stored on an S3 node is the same bytes under the same key as it would be in a device's shard directory, and is hash-verified on read like any device shard.
- **I-53** — A slow or unreachable S3 node never delays a flush beyond the 10 s deadline once ≥ k acks (from any nodes) exist; its slot is recorded as missing and repaired later.
- **I-54** — Multipart completion by chunk-list splice, performed only on the gateway that owns the upload after flushing every part, produces an object byte-identical to streaming concatenation of the parts, with the same ETag.
- **I-55** — No S3 request touches paths outside its bucket: keys with `.`/`..`/empty segments or names beginning with `.` are rejected before any vfs call.
- **I-137** — `add_s3` registers a bucket once: it refuses a name that a row which is not
  removed has, an endpoint and bucket that an S3 row which is not removed has under any
  prefix, an endpoint that is not an http(s) URL, an empty bucket and a zero capacity, and
  a retry with the same ID updates the row it created.
- **I-138** — No DELETE reaches a bucket except from the leader's S3 sweep: the shard
  client refuses `Delete` and `DeleteFenced` on an S3 target without a request, and the
  sweep deletes only objects older than grace that the chunk table does not place on that
  node.
- **I-139** — S3 credentials stay on the device that was given them: they are in
  `<data_dir>/s3nodes.yaml` (mode 0600 where the OS has modes) and never in the FSM, a
  report, a log line or a request to another node.
